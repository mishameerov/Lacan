# Android NPU platform evidence for offline ASR

Checked 2026-10-21 against the primary sources linked below. This is a documentation investigation: no SDK download was accepted, no model compiled, and no device tested. “Supported” below means explicitly listed by that particular integration, not proven support for Lacan's ASR graph. Samsung is one test platform; the product target remains broad Android coverage.

## Model constraints that matter for GigaAM and Whisper

Lacan's existing dynamic-time ONNX CTC graph and GGML Whisper model cannot be passed directly to LiteRT or ExecuTorch. Conversion/export and a backend-specific artifact are separate work. A fixed audio window and an encoder/CTC-first probe reduce the initial shape and decoding problem; this is an engineering proposal, not evidence of successful ASR conversion.

| Backend evidence | Consequence for the conversion probe |
| --- | --- |
| Current ORT QNN EP rejects dynamic shapes and does not support control-flow Loops/Ifs. | Fix batch/time/cache shapes for each chosen artifact. The guide now includes floating-point and quantized HTP execution; do not repeat a universal “QNN is INT8-only” claim from older versions. Existing INT8 ONNX files still need graph/quantization inspection. [Model requirements](https://github.com/onnxruntime/onnxruntime-qnn/blob/main/docs/execution_providers/QNN-ExecutionProvider.md). |
| LiteRT QNN compiler maps floating types and multiple integer types; per-tensor and per-channel quantization are supported, blockwise quantization is explicitly unsupported in its table. Its lowering list includes BatchMatMul, FullyConnected, GELU, convolution and many elementwise ops. | These are compiler mappings, not a guarantee every type/shape executes on every HTP generation. Audit the emitted graph against the exact pinned compiler and actual partitions. [Compiler support table](https://github.com/google-ai-edge/LiteRT/blob/main/litert/vendors/qualcomm/compiler/Qualcomm_QNN_Compiler.md). |
| MediaTek ExecuTorch documents A16W16, A16W8, A16W4, A8W8 and A8W4 precision configurations. | Quantization is a backend recipe requiring calibration and recognition-quality validation. The public guide does not establish arbitrary dynamic-time ASR support. [Quantizer API](https://docs.pytorch.org/executorch/stable/backends-mediatek.html). |
| Samsung ExecuTorch supports FP16 and static 8-/16-bit signed or unsigned quantization. | Start with a supported fixed-shape export; consult the per-op restrictions rather than assuming a transformer is supported from a broad operator claim. [Overview](https://docs.pytorch.org/executorch/stable/backends/samsung/samsung-overview.html), [operator table](https://docs.pytorch.org/executorch/stable/backends/samsung/samsung-op-support.html). |
| Pixel Tensor SDK is a target-specific AOT compiler path. | Do not substitute Coral's Edge TPU compiler or `libedgetpu` for the Pixel SDK. Coral documents its own fully 8-bit, compile-time constant tensor requirements; those are not a documented Pixel G5/G6 compatibility contract. [Coral model requirements](https://www.coral.withgoogle.com/docs/edgetpu/models-intro/), [Coral runtime](https://www.coral.withgoogle.com/docs/edgetpu/inference/). |

Qualcomm AI Hub is useful evidence that optimized speech models and compilation workflows exist: its primary model repository includes multilingual Whisper Base, Medium, Large V3 Turbo and other ASR recipes. AI Hub Workbench is a hosted compile/profile service; its device inventory includes exact, family and proxy devices. Cloud compilation during development is separate from local inference in a shipped app. Do not treat an AI Hub Windows Whisper demonstration as an Android APK demonstration, or a downloadable target artifact as proof that Lacan's graph works. [Model repository](https://github.com/qualcomm/ai-hub-models), [device semantics](https://workbench.aihub.qualcomm.com/docs/hub/devices.html), [Windows app scope](https://aihub.qualcomm.com/apps/whisper_windows_py).

## Offline APK and custom-ROM qualification

LiteRT's current NPU instructions give both Play Feature Delivery modules and an explicit native packaging route. The NPU example requires API 31+ and arm64-v8a, and Qualcomm JNI legacy packaging. Native deployment includes LiteRT, vendor dispatch, backend and DSP libraries plus models; a standalone APK must package the compatible dependencies. On-demand Play delivery cannot satisfy a first offline launch until assets are present. “Online compilation” in this documentation means compilation on the device, not necessarily an inference network request. [NPU deployment instructions](https://developers.google.com/edge/litert/next/npu).

For a no-Play build, qualification must start from the final sideloaded APK in airplane mode, with empty caches, and verify initialization, model access and actual delegation. This is a proposed acceptance test. Custom ROMs add an independent firmware qualification axis: an APK does not install a missing vendor NPU HAL, driver, firmware or device permissions merely by bundling a frontend. Do not use manufacturer/SoC strings as proof of availability.

NNAPI remains worth a bounded compatibility probe on older phones, older Exynos/MediaTek/Snapdragon, Tensor generations absent from the newer SDK lists, and UNISOC. Android explicitly says applications can continue using NNAPI despite its Android 15 deprecation; the Neural Networks HAL continues to be supported. API presence starts at Android 8.1/API 27. Android 10 adds device discovery/assignment, so enumerate the available accelerator and its driver version rather than accepting CPU reference execution as NPU success. [Android API guide](https://developer.android.com/ndk/guides/neuralnetworks), [AOSP module/HAL status](https://source.android.com/docs/core/ota/modular-system/nnapi).

ORT still publishes Android NNAPI packages and documents explicit EP registration. `NNAPI_FLAG_CPU_DISABLED` (API 29+) avoids NNAPI reference CPU execution, but unsupported partitions can still run in ORT CPU kernels; report both assignments. This route can reuse a compatible ONNX graph, although the EP's supported operators and constant-input restrictions can cause partial delegation. Lacan's minimum Android version is currently higher than NNAPI's minimum; this research alone does not add old-OS app support. [ORT NNAPI documentation](https://onnxruntime.ai/docs/execution-providers/NNAPI-ExecutionProvider.html).

## Distribution terms and unresolved open-source compatibility

Open-source integration code does not establish redistribution rights for proprietary vendor compilers, runtime binaries, DSP skeletons or firmware. Record the exact downloaded archive, license, notices, permitted redistribution files and target restrictions before shipping. No Qualcomm, MediaTek or Samsung SDK archive license was accepted or audited here; their GPL compatibility remains unresolved. Dynamic loading alone is not a legal compatibility determination.

Google Tensor has particularly concrete public restrictions requiring attention: SDK terms §4.7 restrict SDK redistribution; §4.9 separately preserves open-source component licenses; §4.16 requires prior written authorization to distribute software or products created using the SDK; §§4.17–4.18 restrict cross-device benchmarking and publication of Tensor performance data. These are observations about the published terms, not a legal conclusion about Lacan. Resolve authorization and the specific runtime distribution terms before describing Tensor as a generally redistributable GPL-compatible backend. [Google Tensor SDK terms](https://developers.google.com/edge/litert/next/tensor_ml_terms).

The practical platform policy is therefore capability-tested vendor acceleration, a retained legacy NNAPI probe where firmware provides useful drivers, and GPU/CPU fallback. Keep results keyed by model hash, runtime/compiler version, SoC, OS/ROM and driver; a single Samsung bench result cannot establish the cross-vendor product claim.
