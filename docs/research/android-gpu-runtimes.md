# Portable Android GPU ASR runtimes

Primary-source review: **2026-10-21**. Research only: no device commands, builds, model conversion or inference were performed. This supplements [the integration plan](../android-acceleration.md). “Supported” below distinguishes an implemented ASR pipeline from a generic tensor backend; none is a demonstrated Lacan Android GPU result.

## Decision

There is no universal accelerator that makes all existing ONNX/GGML models fast on all Android GPUs. The strongest first model-specific comparisons are **published Parakeet TDT v3 LiteRT artifacts** and **the official ExecuTorch Parakeet Vulkan exporter/Android runner**. Investigate **native ONNX Runtime WebGPU** alongside them to preserve the current ONNX family. A bounded GigaAM CTC conversion remains the next controlled experiment for Lacan's already-tested Russian model; **ncnn's upstream Whisper Vulkan example** is a concrete alternative Whisper implementation. See [exact artifact and conversion evidence](android-asr-conversion.md). The failed legacy whisper.cpp CPU experience does not establish a GPU result; a separate Vulkan experiment remains optional, with explicit user buy-in before reviving that engine as a product direction.

“Portable” should mean one application/runtime family with qualified artifacts and runtime capability checks, plus an honest CPU fallback. It cannot mean every device, every driver, every graph, or all decoding on the GPU.

## Graph, precision and memory constraints

For **native ORT WebGPU**, compare exact graph nodes/types/opsets against the native kernel registry, not the similarly named browser/JSEP operator table. The reviewed native registry includes `Conv`, `MatMul`, `Softmax` and `LayerNormalization`, making an FP32 Conformer/CTC graph plausible; that does not establish every GigaAM node/shape as supported. `DynamicQuantizeLinear` and `MatMulInteger` are absent from that registry snapshot. If Lacan's INT8 Whisper artifact uses that dynamic-quantization chain, it may keep the expensive path on CPU or require another artifact; INT8 is not automatically the best GPU candidate. Audit the actual encoder/decoder graphs before claiming coverage, then inspect runtime partitions. The source and published builds can differ. [Native kernel registration](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/providers/webgpu/webgpu_execution_provider.cc), [browser-specific table, for distinction](https://github.com/microsoft/onnxruntime/blob/main/js/web/docs/webgpu-operators.md).

The simplest first graph is GigaAM **CTC encoder + CTC projection**, using fixed or bounded audio windows and CPU token collapse. This avoids a token-generating decoder. The conversion still needs convolution/subsampling, normalization, attention, masks, reshapes and tensor-axis semantics verified against the original graph. Dynamic time is not automatically impossible on a GPU, but each lowering and kernel must support the allowed shape range. Test multiple lengths; a trace that freezes a length can look correct on its export sample and fail elsewhere. ncnn explicitly provides dynamic shape/subscript expressions, with scalar shape work on CPU. [ncnn expression handling](https://github.com/Tencent/ncnn/wiki/expression).

Whisper requires feature parity, an encoder, decoder cache/position handling and a host decoding policy. Repeated per-token submissions and output reads can dominate even if matrix kernels accelerate. Parakeet **CTC**, **RNN-T** and **TDT** need separate compatibility decisions: an encoder-only GPU with CPU predictor/joiner or TDT loop may be sensible, but cannot be reported as an entirely GPU pipeline. Preserve bounded cache/workspace sizes and cancellation between submissions. These are integration hypotheses to validate, not performance claims.

Use FP32 parity as the first control, then FP16 where the runtime/model tolerates it. Check logits/encoder errors and actual Russian/English WER/CER, including silence and difficult audio; matching one clean transcript is insufficient. The upstream ncnn Whisper FP16 disablement is a concrete reason to avoid assuming half precision is harmless. ExecuTorch's Vulkan quantization is **linear-layer-specific**: INT8/INT4 weights and supported activation recipes do not establish all Conformer convolutions or normalization as INT8. Its operator registry also has dimensional constraints, e.g. convolution variants and resize restrictions. [Quantization](https://docs.pytorch.org/executorch/stable/backends/vulkan/vulkan-quantization.html), [operators](https://docs.pytorch.org/executorch/stable/backends/vulkan/vulkan-op-support.html).

Do not equate on-disk INT8 with integer GPU arithmetic or peak-memory savings. The older LiteRT GPU delegate uses floating-point execution for quantized graphs and CPU quantize/dequantize at I/O; unsupported nodes can split the graph and create expensive synchronization. This is a documented warning for that delegate, not proof that every new CompiledModel kernel behaves identically. [LiteRT GPU limitations](https://developers.google.cn/edge/litert/performance/gpu).

LiteRT exposes `TensorBuffer` interop and asynchronous fences for OpenCL/OpenGL/AHardwareBuffer. This helps when producer and consumer already use compatible GPU buffers; microphone PCM/features in CPU memory still need an actual transfer plan. Reusing buffers, keeping encoder output/cache resident and minimizing GPU→CPU→GPU partitions are more meaningful than calling a Java array “zero copy.” [Buffer API](https://developers.google.com/edge/litert/inference). ncnn's AHardwareBuffer example concerns camera/surface images and needs API 26 plus a suitable build; it does not eliminate audio uploads. [AHB requirements](https://github.com/Tencent/ncnn/wiki/use-ncnn-with-android-hardware-buffer).

## Hardware, custom ROMs and distribution

| Device family | Honest portability expectation |
| --- | --- |
| Adreno | Qualify LiteRT CL/GL and Vulkan on exact driver; Qualcomm-specific QNN is a separate optimization. |
| Mali / Immortalis | Qualify CL/GL and Vulkan independently; newer Arm VGF is a separate ML SDK/TOSA path requiring Vulkan 1.3, not automatic support from an Arm GPU name. |
| Xclipse | A Vulkan/OpenGL candidate where the actual driver provides required features; neither desktop AMD results nor Mali qualification applies. |
| PowerVR | Treat as unqualified until exact devices pass; generic API presence and ncnn's theoretical compatibility are insufficient ASR evidence. |

Android supplies the Vulkan loader from API 24, but an app must enumerate physical devices and required features; the loader can return no usable devices. An OS version or SoC name is not a capability test. [NDK native APIs](https://developer.android.com/ndk/guides/stable_apis), [extension checks](https://developer.android.com/ndk/guides/graphics/extensions). For custom ROMs, qualify the installed vendor GPU stack; an open-source runtime does not replace missing or incompatible kernel/userspace drivers. OpenCL is not a public NDK API guarantee; LiteRT's OpenGL alternative is valuable, but requires its own graph qualification.

ExecuTorch 1.5 docs include Arm VGF and Samsung entries beyond the shorter Android integration table. **Presence in docs/main source is not proof a particular prebuilt AAR contains it.** VGF needs ML SDK for Vulkan and a compatible driver; no reviewed Whisper/GigaAM/Parakeet VGF recipe makes it a current primary route. [Backend catalog](https://docs.pytorch.org/executorch/1.5/android-backends.html), [VGF requirements](https://docs.pytorch.org/executorch/1.5/backends/arm-vgf/arm-vgf-overview.html).

These routes can perform inference offline after native libraries and models are installed; a sideloadable APK should package its runtime dependencies and avoid first-run Play downloads. GPU driver availability remains device/ROM-dependent. Runtime source licenses are permissive, but retain notices and check models and transitive components separately: [LiteRT Apache-2.0](https://github.com/google-ai-edge/LiteRT/blob/main/LICENSE), [ExecuTorch BSD-style](https://github.com/pytorch/executorch/blob/main/LICENSE), [ncnn BSD-3-Clause](https://github.com/Tencent/ncnn/blob/master/LICENSE.txt), [MNN Apache-2.0 repository](https://github.com/alibaba/MNN), [IREE Apache-2.0 with LLVM exceptions](https://github.com/iree-org/iree/blob/main/LICENSE), [transcribe.cpp MIT](https://github.com/handy-computer/transcribe.cpp#license). Redistribution of proprietary drivers is not granted by those licenses.

## Recommended bounded experiments

1. **ORT WebGPU feasibility gate:** establish an exact compatible ORT/Dawn Android ARM64 build/registration recipe and operator coverage for the current FP32 CTC ONNX model. Stop if packaging/core compatibility is unreasonable; do not modify the bundled sherpa runtime blindly. No inference is needed to decide whether the source integration is tractable.
2. **Parakeet runtime comparison:** qualify the published LiteRT TDT v3 5-second FP32 artifact against its CPU reference and inspect GPU assignment; independently follow the official ExecuTorch Parakeet Vulkan exporter/Android runner. Keep host TDT decoding explicit and account for transfers, state and padding. Freeze exact model/export/runtime revisions. These existing paths avoid making runtime evaluation depend on inventing a GigaAM exporter.
3. **One alternative if Whisper is desired:** inspect/reproduce ncnn's upstream export and FP32 Vulkan pipeline before attempting FP16 or INT8. Compare conversion/integration cost with optional whisper.cpp Vulkan using existing weights; do not silently reactivate the legacy engine.
4. **GigaAM CTC conversion gate:** export one bounded FP32 CTC graph, prove converted CPU parity, then inspect LiteRT GPU partitions. If concrete operators block it, compare PyTorch export plus `VulkanPartitioner`. This preserves focus on the already-tested Russian model after the existing Parakeet runtime paths. Reserve MNN/IREE/VGF for a specific demonstrated advantage or resolved converter gap.

Only after explicit authorization for device testing: qualify one Adreno, one Mali/Immortalis and the target Xclipse phone, then additional PowerVR/custom-ROM devices. Capture actual backend/partitions, cold and warm initialization, total transcription/finalization latency, peak resident/native/GPU memory, accuracy and thermal stability. Kernel-only or desktop numbers are not acceptance evidence. Keep failed initialization and poor end-to-end results visible, and retain the working CPU path.
